## 1. LIBERO → LeRobot Adapter (DONE)

### Status: COMPLETE

**File**: `examples/integration/libero_to_lerobot.py` — 710 lines, fully functional.

This converter is the critical unblocking piece for StarVLA-DHB training (Section 2).
StarVLA's dataloader expects LeRobot v2.0 parquet format; LIBERO provides HDF5 files.

### LeRobot v2.0 Output Structure

The converter produces a fully spec-compliant LeRobot v2.0 dataset:

```
dataset_root/
  meta/
    modality.json          # State/action/video modality definitions
    info.json              # Dataset-level metadata (num_episodes, fps, etc.)
    episodes.jsonl         # One JSON line per episode (index, length, task_index)
    tasks.jsonl            # Task name → index mapping
    stats_gr00t.json       # Per-column statistics (min/max/mean/std) for normalization
  data/
    chunk_000000/
      episode_000000.parquet
      episode_000001.parquet
      ...episode_000015.parquet    # 16 episodes per chunk
    chunk_000001/
      episode_000016.parquet
      ...
  videos/
    chunk_000000/
      episode_000000_primary_image.mp4
      episode_000000_wrist_image.mp4
      ...
```

### Input: LIBERO HDF5 Structure

```
demo_X/
  actions: [T, 7]              # joint target velocities (OSC_POSE space)
  robot_states: [T, 9]         # [gripper_state(2), ee_pos(3), ee_quat_wxyz(4)]
  agentview_rgb: [T, H, W, 3]  # 128×128 overhead camera
  wrist_rgb: [T, H, W, 3]      # 128×128 wrist camera (optional)
```


### DHB Invariants as Optional Columns

The adapter adds DHB-DR invariants as optional parquet columns:
- `dhb.linear_invariants`: shape `(T, 4)` — `[m_i, φ_x, φ_y, φ_z]` per timestep
- `dhb.angular_invariants`: shape `(T, 4)` — `[ω_i, ψ_x, ψ_y, ψ_z]` per timestep

These are populated from a precomputed pickle file (generated by
`examples/integration/precompute_dhb_invariants.py`). StarVLA's DHBActionHeader
uses these columns as supervised targets for the invariant head during training.

### 5 Required Metadata Files

The converter generates all 5 metadata files required by StarVLA:

| File | Content | Key fields |
|------|---------|-----------|
| `meta/modality.json` | Camera/state/action definitions | video keys, state dim=9, action dim=7 |
| `meta/info.json` | Dataset summary | num_episodes, fps=10, chunk format |
| `meta/episodes.jsonl` | Per-episode metadata | episode_index, length, task_index |
| `meta/tasks.jsonl` | Task name-to-index mapping | task_index, task_name |
| `meta/stats_gr00t.json` | Normalization statistics | min/max/mean/std per column |

```python
# Copy WM4A_OFT.py, change two lines:
@FRAMEWORK_REGISTRY.register("WM4A_DHB")   # was "WM4A_OFT"
class WM4A_DHB(WM4A_OFT):
    def __init__(self, config):
        super().__init__(config)
        # Override action model with DHB head
        from ...action_model.DHBActionHeader import get_action_model
```

### Expected Performance

Based on StarVLA-FAST (97.8%) and StarVLA-MLP (97.1%) results from the StarVLA paper:

| Metric | Expected value | Basis |
|--------|---------------|-------|
| In-distribution success (0cm) | ≥97% | StarVLA backbone is strong; DHB head is at least as good as MLP |
| 5cm perturbation | ≥80% | DHB geometric encoding provides exact invariance; needs real-world validation |
| 10cm perturbation | ≥70% | Primary paper claim |
| 20cm perturbation | ≥50% | Stretch goal |

The geometric sweep already shows 0.0mm error at all offsets (Exp 1). The policy
success rate should reflect this once training converges, though object detection
errors and grasping accuracy also contribute.

### Risk: OSC Action Space

StarVLA is trained on raw OSC actions. If DHB invariants are decoded to absolute
end-effector poses and then converted back to OSC actions via an IK + PD controller,
there may be a distribution mismatch. Two options:

1. **End-effector pose targets** (recommended): Train DHBActionHeader to predict
   EEF pose trajectories; use the existing embodik VelocityIK solver at inference.
2. **Direct OSC action prediction**: Train on OSC actions directly (existing LIBERO
   demos), but encode DHB invariants in the input observation to help the policy
   generalize geometrically.

Option 2 is simpler and more compatible with the existing LIBERO data format.

## 3. Proper Simulation Perturbation

### Status: DESIGN COMPLETE — implementation pending (Week 3-4)

### Problem

Current LIBERO simulation runs naive replay at 0cm (100% success) but DHB at 0cm
and 5cm shows only gripper moving. Root cause: LIBERO's OSC_POSE controller has
non-constant scale factors (20×–577× per-step variation).

See full analysis in `notes/supplementary/03_simulation_analysis.md`.

### Solution: Object Perturbation + Waypoint PD Controller

The correct experiment design for the simulation evaluation:

1. **Object perturbation**: Move object in `init_state`, not robot start pose
2. **DHB adaptation**: Decode DHB invariants from new object location as initial pose
3. **Waypoint PD controller**: Use adapted EEF trajectory as waypoints; compute OSC
   actions via proportional control at each step

#### Step 1: Patch `init_state` to Include Object Position

LIBERO state vector format (92-dimensional):
```
indices 0-6:   robot joint positions
indices 7-13:  robot joint velocities
indices 14-20: robot EEF position + quaternion (wxyz)
indices 21+:   object states (position + quaternion + velocity per object)
```

To perturb object position:
```python
import numpy as np
from libero.envs import OffScreenRenderEnv

env = OffScreenRenderEnv(bddl_file_name=bddl_path, camera_heights=128, camera_widths=128)
env.reset()
env.set_init_state(demo_init_state)

# Identify object position indices via qpos inspection
sim = env.sim
obj_name = "black_bowl"   # target object
obj_joint = f"{obj_name}_joint0"
qpos_idx = sim.model.get_joint_qpos_addr(obj_joint)  # returns (start, end) tuple

# Perturb object position (only XY, keep Z constant to maintain table contact)
modified_state = demo_init_state.copy()
modified_state[qpos_idx[0]:qpos_idx[0]+3] += np.array([0.0, 0.05, 0.0])  # +5cm Y
env.set_init_state(modified_state)
env.sim.forward()  # Apply state change

# Now get the new object position as the DHB adaptation target
new_obj_pos = env.sim.data.body_xpos[env.sim.model.body_name2id(obj_name)]
```

#### Step 2: DHB Adaptation from New Object Location

```python
from dhb_xr.encoder.dhb_dr import encode_dhb_dr
from dhb_xr.decoder.dhb_dr import decode_dhb_dr

# Encode demo with original object as anchor
result = encode_dhb_dr(demo_positions, demo_quaternions,
                        init_pose={'position': orig_obj_pos, 'quaternion': demo_q[0]})

# Decode from new object location
adapted = decode_dhb_dr(result['linear_motion_invariants'],
                          result['angular_motion_invariants'],
                          initial_pose={'position': new_obj_pos,
                                         'quaternion': demo_q[0]})
adapted_positions = adapted['positions']    # (N, 3)
adapted_quaternions = adapted['quaternions']  # (N, 4)
```

#### Step 3: Waypoint PD Controller

```python
Kp_pos = 10.0   # proportional gain (tune per task)
Kp_rot = 5.0    # rotational gain
max_action = 1.0
tol_pos = 0.01  # 1cm convergence tolerance

for waypoint_pos, waypoint_quat, gripper_cmd in zip(
        adapted_positions, adapted_quaternions, demo_gripper):
    for step in range(max_steps_per_waypoint):
        curr_pos = obs['robot0_eef_pos']
        curr_quat = obs['robot0_eef_quat']  # xyzw convention in LIBERO obs

        pos_error = waypoint_pos - curr_pos
        if np.linalg.norm(pos_error) < tol_pos:
            break  # waypoint reached

        action = np.zeros(7)
        action[:3] = np.clip(Kp_pos * pos_error, -max_action, max_action)
        # Orientation error via quaternion difference
        # action[3:6] = rotation_error_to_axis_angle(curr_quat, waypoint_quat) * Kp_rot
        action[6] = gripper_cmd  # binary: 1=close, -1=open
        obs, reward, done, info = env.step(action)
```

### Expected Outcome After Fix

With waypoint PD + object perturbation:
- DHB at 0cm: ~same as naive (~100%, controller reaches correct positions)
- DHB at 5cm: should be ≥70% (geometric error is 0mm, task success depends on grasping)
- Naive at 5cm: ~0% (OSC actions target wrong location)

## 4. Cross-Embodiment: embodik Dual-Arm ECTS Validation

### Status: PLANNED — post-training validation

### Goal

Demonstrate DHB-XR generalization across robot embodiments using the embodik
framework's dual-arm setup. This is the "cross-embodiment" claim in §5 (Discussion).

### What is ECTS?

ECTS = Extended Cartesian Trajectory Sharing. The embodik framework supports:
- Specifying EEF trajectories in Cartesian space
- Solving IK for arbitrary robot morphologies via `VelocityIK`
- Running the same Cartesian trajectory on different robots (single-arm, dual-arm, humanoid)

embodik's `VelocityIK` already runs in 1.5 µs/step on CPU (6ms for 98-step trajectories).

### Proposed Validation

**Setup**: Encode a LIBERO-Spatial demo (Panda 7-DOF) with DHB-DR. Decode and execute
on a simulated iiwa dual-arm system via embodik ECTS.

**Expected result**: The spatial generalization (0mm endpoint error) should hold across
embodiments because DHB operates in Cartesian EEF space — the IK solver handles the
joint-space differences.

**Implementation**:
```python
from embodik.kinematics import VelocityIK
from dhb_xr.encoder.dhb_dr import encode_dhb_dr
from dhb_xr.decoder.dhb_dr import decode_dhb_dr

# Encode single-arm Panda demo
result = encode_dhb_dr(panda_positions, panda_quaternions)

# Decode at perturbed pose (embodiment-agnostic)
adapted = decode_dhb_dr(result['linear_motion_invariants'],
                          result['angular_motion_invariants'],
                          initial_pose=iiwa_start_pose)

# Execute on iiwa via embodik VelocityIK
ik = VelocityIK(robot_urdf='iiwa14.urdf')
for target_pos, target_quat in zip(adapted['positions'], adapted['quaternions']):
    joint_vels = ik.solve(target_pos, target_quat, current_joints)
    # send joint_vels to iiwa controller
```

## 5. Flow-Matching Integration

### Status: DESIGN STAGE — for journal extension

### Motivation

π0 (Black et al., 2024) achieves state-of-the-art dexterous manipulation via
conditional flow matching over raw action trajectories. DHB-XR complements this by
providing SE(3)-invariant representations. The natural combination is a flow-matching
head that operates over DHB invariants rather than raw actions.

### π0-Style FM Head for DHB Invariants

Replace the StarVLA MLP/FAST action head with a flow-matching head over DHB invariant
sequences:

```
visual_language_tokens  →  VLM backbone  →  hidden (B, S, 2048)
dhb_invariants_noised   →  concat        →  FM head  →  dhb_invariants_clean
                                                       →  decode_dhb_dr
                                                       →  EEF trajectory
                                                       →  VelocityIK
                                                       →  joint commands
```

The FM head predicts the "velocity field" in DHB invariant space:
```
v_θ(Ĩ_t, t, h_VLM) = Ĩ_0 - Ĩ_1     [flow from noise to clean invariants]
```

where `Ĩ_t = (1-t) * Ĩ_noise + t * Ĩ_clean` is the FM interpolation.

**Advantage over raw-space FM**:
- DHB invariants are SE(3)-invariant → the FM learns motion shapes, not absolute poses
- Smaller prediction space (8-dim invariants vs 7-dim × T raw actions)
- Invariant space is smoother (no discontinuities from absolute coordinates)

### Implementation Plan

```python
# DHBFlowMatchingHead (extends DHBActionHeader)
class DHBFlowMatchingHead(nn.Module):
    def __init__(self, input_dim=2048, invariant_dim=8, chunk_len=50,
                 num_diffusion_steps=10):
        self.inv_noise = nn.Parameter(torch.randn(chunk_len, invariant_dim))
        self.score_net = TransformerScoreNet(...)  # predicts velocity field

    def forward(self, hidden, invariants_target=None):
        # Training: add noise, predict denoising direction
        t = torch.rand(B, device=hidden.device)
        noise = torch.randn_like(invariants_target)
        inv_noised = (1-t.view(B,1,1)) * noise + t.view(B,1,1) * invariants_target
        v_pred = self.score_net(inv_noised, t, hidden)
        v_true = invariants_target - noise
        loss = F.mse_loss(v_pred, v_true)
        return loss

    def predict_invariants(self, hidden, num_steps=10):
        # Euler ODE integration from noise to clean
        inv = torch.randn(B, chunk_len, invariant_dim)
        for t in torch.linspace(0, 1, num_steps):
            v = self.score_net(inv, t * torch.ones(B), hidden)
            inv = inv + (1/num_steps) * v
        return inv
```

### Expected Benefits

- Better handling of multimodal task distributions (FM can represent multiple solutions)
- Smoother invariant trajectories (FM regularizes the prediction path)
- Potential further improvement on 10cm+ perturbations

### Risk and Timeline

- Risk: FM in invariant space may be no better than in raw space for simple tasks
- Test on LIBERO-Spatial before committing to journal write-up
- Timeline: 3-4 weeks (implement + train + evaluate)

## 6. Contact-Rich Extension

### Status: RESEARCH DIRECTION — 6-12 month horizon

### Problem

DHB-XR assumes a smooth, continuous EEF trajectory without contact changes.
Contact-rich tasks (peg-in-hole, assembly, screwing) have trajectory segments with
qualitatively different behavior: free-space approach, contact acquisition, guided
insertion, release.

A single DHB invariant encoding treats the entire trajectory uniformly, which:
- Creates spurious invariants at contact transitions (discontinuous derivatives)
- Loses information about which segments are "contact-constrained" vs "free"

### Proposed: Segment-Wise Invariant Encoding

**Segment detection**: Identify contact transitions from force/torque data or
gripper state changes:
```python
segments = detect_segments(trajectory, ft_data)
# segments = [(0, 45, 'free'), (45, 62, 'contact'), (62, 98, 'insertion')]
```

**Per-segment encoding**: Apply DHB-DR independently to each segment:
```python
invariants_by_segment = []
for start, end, segment_type in segments:
    seg_inv = encode_dhb_dr(positions[start:end], quaternions[start:end])
    invariants_by_segment.append({
        'type': segment_type,
        'invariants': seg_inv,
        'start_pose': {'position': positions[start], 'quaternion': quaternions[start]},
        'end_pose': {'position': positions[end], 'quaternion': quaternions[end]},
    })
```

**Segment-wise adaptation**:
```python
for i, seg in enumerate(invariants_by_segment):
    if seg['type'] == 'free':
        # Standard DHB adaptation (0mm endpoint error)
        adapted_seg = adapt_free_segment(seg, new_target)
    elif seg['type'] == 'contact':
        # Force-guided: maintain contact force direction, adapt approach
        adapted_seg = adapt_contact_segment(seg, surface_normal)
    elif seg['type'] == 'insertion':
        # Compliance-aware: use compliant motion primitives
        adapted_seg = adapt_insertion_segment(seg, hole_location)
```

**Transition handling**: The end pose of segment i becomes the initial pose for
segment i+1. SE(3) invariance holds within each free segment; contact segments
require additional contact geometry information.

### Required Infrastructure

1. **Force/torque segmentation**: `src/dhb_xr/preprocessing/contact_segmentation.py`
2. **Per-segment encoder**: extend `encode_dhb_dr` to handle segment lists
3. **Compliant motion primitives**: force-based adaptation for contact segments
4. **Test tasks**: RoboCasa assembly tasks or RLBench peg-in-hole

### Timeline

- Contact segmentation: 2 weeks
- Per-segment adaptation: 3 weeks
- Test on 1 contact-rich task: 1 week
- Expected: DHB-XR + segments >> DHB-XR monolithic for peg-in-hole by ≥20%
